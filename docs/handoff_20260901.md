## 3. 当前运行链路

正式 Gameplay 当前使用以下链路：

```text
模式入口
  -> ModeQuestionDirector / TowerDirector
  -> QuestionRequest
  -> QuestionCompiler
  -> QuestionCompilerEngine
  -> QuestionInstance
```

`QuestionCompiler` 是正式游戏的统一出题入口。旧 `QuestionGenerator`、`ExtendedQuestionGenerator`、`QuestionTypeCatalog`、`StaticQuestionBank` 和旧静态加载器均已删除。

### 3.1 模式状态

- 试炼塔：保留独立的楼层/通关要求导演，由 `TowerDirector` 产生请求，再交给统一编译器。
- 好友挑战：按创建者选择的主题和规则生成；相同种子与配置可复现相同题序，不受本地历史影响。
- 无尽乱斗：超过原 60 秒阶段边界后仍可持续出题，直到生命耗尽。
- 每日主题：同一天固定随机主题；玩家每次重新开局使用不同运行种子，题目内容不同。
- 普通模式与每日模式会使用跨局事实、答案和语义签名冷却，降低短期重复。

这意味着当前虽然统一了入口，但内部仍以 family 充当模板路由键。下一阶段必须删除该层，不能只把字段改名。

## 5. 下一阶段目标模型

建议以模板为唯一题型实体：

```ts
interface QuestionTemplate {
  id: string;
  theme: ThemeId;
  engine: GameplayEngineId;
  capabilities: QuestionCapability[];
  tags: string[];
  sourceKind: 'algorithmic' | 'reviewed-facts';
  difficultyBands: DifficultyBand[];
  supportedRuleSets: RuleId[][];
  enabled: boolean;
}

interface QuestionInstance {
  id: string;
  templateId: string;
  theme: ThemeId;
  engineId: GameplayEngineId;
  factIds: string[];
  contentVersion: string;
  // prompt、targets、activeRules 等运行时字段
}
```

约束：

- `theme` 必须是显式字段，不能从 `templateId` 字符串推断；
- `templateId` 是稳定且唯一的模板标识，不承担主题或 family 解析职责；
- 模式只使用 `themes + capabilities + tags + rules + difficulty` 选题；
- `factIds` 只追踪素材来源；
- 删除 `familyId`、`familyKind`、`typeId` 和 variant 凑题型逻辑。

## 6. 建议迁移顺序

### 阶段 1：建立独立模板注册表

1. 将当前 `META` 和生成器路由合并为显式模板定义。
2. 每个模板直接绑定编译处理器或稳定的算法键。
3. 为模板声明完整规则兼容、难度、能力和标签。
4. 禁止默认兜底生成；未知模板必须立即报错。

### 阶段 2：改造编译器

1. `QuestionCompilerEngine.compile()` 接收 `QuestionTemplate` 和 `QuestionRequest`，不接收 `ContentFamilySpec`。
2. 所有生成函数改为接收模板上下文，不再传递 family。
3. 语义签名改为使用 `templateId`，删除对 `familyId` 和 `typeId` 的回退读取。
4. `QuestionInstance` 始终写入稳定 `templateId`、`factIds`、`contentVersion`。

### 阶段 3：改造规则与模式策略

1. 将 family 规则表迁为模板能力和显式规则兼容表。
2. 将目标数量上限迁为模板属性或能力策略。
3. 试炼塔删除 `familyKinds`，只保留主题、能力、标签、规则、难度和通关指标。
4. 好友挑战、每日和无尽模式继续只产生 `QuestionRequest`。

### 阶段 4：改造事实注册

1. `QuestionBankPack.familyKinds` 改为 `templateIds` 或事实查询标签。
2. 将事实结构统一为带稳定 ID、kind、tags、来源、审核状态和审核时间的记录。
3. 将可复用的旧静态 JSON 逐包迁移和审计，不直接恢复旧 schema。

### 阶段 5：删除兼容字段

按依赖顺序删除：

1. `TemplateCompileDirective` 的 family 字段；
2. `QuestionTemplate.family`；
3. `ContentFamilySpec` 与 `ContentFamilyKind`；
4. `QuestionInstance.familyId` 与 `typeId`；
5. 所有 family 命名的策略函数、测试夹具和统计字段。
